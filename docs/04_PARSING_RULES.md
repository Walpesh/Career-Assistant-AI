# 04_PARSING_RULES.md
# Правила парсинга и обхода защит hh.ru

## 1. Цели и ограничения

- Максимально устойчивый сбор вакансий без официального API hh.ru
- Минимизация риска блокировки IP и аккаунтов
- Предсказуемое поведение при появлении капчи и rate-limit
- Контролируемый параллелизм и прозрачная очередь задач

**Жёсткие лимиты (на одного пользователя):**
- Максимум 2 одновременных парсинг-воркера
- Не более 60–80 запросов с одного IP
- Случайная задержка 4–8 секунд между запросами
- Рекомендуемый суточный объём: 300–500 вакансий

---

## 2. Стратегия парсинга (Fallback Chain)

Парсинг всегда идёт по цепочке от самого быстрого к самому надёжному методу:

1. **curl_cffi** (основной быстрый путь)
   - Impersonate современных версий Chrome
   - Извлечение данных из `HH-Lux-InitialState` (встроенный JSON)
   - Используется для списков вакансий и отдельных карточек

2. **Playwright + stealth** (основной надёжный путь)
   - playwright-stealth / Patchright / Nodriver
   - Полная эмуляция браузера + human-mimicry
   - Используется при неудаче curl_cffi или при подозрении на защиту

3. **Ручное вмешательство / сервис капчи**
   - При появлении капчи задача переводится в статус `failed` или `waiting_captcha`
   - Опционально: интеграция с 2Captcha / CapSolver

## 3. Proxy & Anti-Ban Module

### 3.1. Требования к прокси
- **Только резидентные прокси** (Residential)
- Датацентровые прокси запрещены (быстро банятся)
- Желательно прокси из российских подсетей (или страны пользователя)

### 3.2. Политика ротации
- Sticky-сессия: 5–10 минут на один IP
- Или принудительная смена после 60–80 запросов
- При получении 429 / капчи / серии 404 — немедленная смена IP + пауза

### 3.3. Обязательные техники маскировки
- Ротация реальных User-Agent (последние Chrome, Firefox, Safari)
- Полный набор браузерных заголовков (`Accept`, `Accept-Language`, `Sec-Fetch-*` и т.д.)
- Сохранение и переиспользование cookies внутри сессии
- Прогрев сессии: первый запрос всегда на `https://hh.ru/`
- Случайные задержки 4–8 секунд (лучше нормальное распределение)
- Human-mimicry в Playwright:
  - Движения мыши по кривым Безье
  - Случайный скролл
  - Небольшие паузы «чтения» страницы

## 4. Логика работы с разными режимами

### 4.1. Автопоиск
1. Формирование поискового URL hh.ru на основе ключевых слов и фильтров
   (фильтры **комбинируются**: занятость, формат работы и график могут быть
   заданы одновременно, любое количество значений в каждом)
2. Парсинг страниц результатов (с ограничением `max_pages`)
3. Для каждой карточки — переход на детальную страницу
4. Извлечение только необходимых данных (шапка + описание)
5. Дедупликация и сохранение в БД

### 4.2. Групповой парсер
1. Пользователь передаёт готовую ссылку результатов поиска
2. Система обходит страницы пагинации (с лимитом)
3. Далее — аналогично Автопоиску

### 4.3. Ручное добавление
1. Пользователь передаёт прямую ссылку на вакансию
2. Один запрос на детальную страницу
3. Сохранение + опциональный запуск анализа

### 4.9. Чёрный список слов

Дополнительный фильтр, включаемый **тумблером** в режимах «Автопоиск» (§4.1) и
«Групповой парсер» (§4.2). Поля запроса: `blacklist_enabled` (тумблер),
`blacklist_words[]` (слова, максимум 50).

1. Нормализация списка: обрезка пробелов, отсечение пустых, дедупликация без
   учёта регистра, ограничение длины списка.
2. **Перед сохранением вакансии в БД** ищется совпадение каждого слова в тексте
   вакансии (название, компания, описание). Поиск регистронезависимый.
3. Если слово найдено — вакансия **не сохраняется**; ранее сохранённая вакансия
   с тем же `hh_vacancy_id` **удаляется из БД** вместе с анализом и письмом.
4. Счётчик отсева попадает в `tasks.result` как `blacklisted`.
5. При выключенном тумблере слова в задачу не передаются, поведение полностью
   совпадает со старым: применяются только фильтры поиска и настройки задачи.

## 5. Обработка ошибок и защит hh.ru

| Ситуация                        | Действие системы                                      | Статус задачи      |
|--------------------------------|-------------------------------------------------------|--------------------|
| HTTP 429                       | Смена прокси + exponential backoff                    | processing → retry |
| Капча                          | Остановка воркера, уведомление пользователя           | failed / waiting_captcha |
| Серия 404 на карточках         | Считается троттлингом → пауза 30–60 сек + смена IP    | retry              |
| Изменение вёрстки              | Fallback на Playwright + логирование                  | processing         |
| Вакансия реально удалена       | Помечается как error с причиной "not_found"           | completed          |
| Превышен лимит пользователя    | Задача ставится в очередь и ждёт освобождения слота   | pending            |

## 6. Очередь парсинга (Queue Rules)

- Все задачи парсинга проходят через единый **Queue Manager**
- Приоритеты (от высшего к низшему):
  1. Ручное добавление одной вакансии
  2. Групповой парсер
  3. Автопоиск
- На одного пользователя одновременно может работать не более **2** парсинг-воркеров
- LLM-задачи всегда выполняются в отдельной строгой очереди (1 воркер на всё приложение или per-user)

### 6.1. Реализация: Redis + ARQ (событийная очередь)

Очередь построена на **Redis + ARQ**. База данных не используется как источник
работы: короткого опроса `SELECT ... FROM tasks WHERE status = 'pending'` нет.

| Этап | Механизм |
|------|----------|
| Создание задачи | API вставляет запись в `tasks` и сразу вызывает `enqueue_job()` |
| Хранение очереди | Отсортированное множество Redis (`career:queue:parsing`, `career:queue:llm`) |
| Взятие задачи | ARQ-воркер читает очередь `ZRANGEBYSCORE` по score'у |
| Порядок | Приоритет задан score'ом: ручное → групповое → авто |
| Дедупликация | Стабильный `_job_id = <task_type>:<task_id>` |
| Ограничение парсинга | Redis-семафор `parsing:<user_id>` на 2 слота (`SET NX EX`) |
| Ограничение LLM | Очередь `career:queue:llm` с `max_jobs=1` + глобальный слот `llm` |
| Занятый слот | Задача остаётся `pending`, job откладывается через `Retry(defer=...)` |
| Восстановление | При старте зависшие `pending`/`processing` возвращаются в очередь (разово) |

**Простой системы не порождает SQL-запросов:** воркер ждёт работу в Redis,
таблица `tasks` обновляется только при смене состояния задачи.

### 6.2. Запуск воркеров

Встроенный режим (по умолчанию) — воркеры поднимаются в lifespan FastAPI:

```bash
uvicorn app.main:app
```

Отдельные процессы (для горизонтального масштабирования парсинга, §6
архитектуры docs/01):

```bash
arq app.modules.queue_manager.worker:ParsingQueueSettings   # парсинг, масштабируется
arq app.modules.queue_manager.worker:LLMQueueSettings       # LLM, строго один процесс
```

### 6.3. Realtime-события

Воркер публикует события в Redis-канал, API-процесс читает его и отправляет
события в WebSocket. Поэтому события доходят до фронтенда одинаково — и при
встроенных, и при отдельных воркерах.

| Событие | Когда |
|---------|-------|
| `task.created` | Задача создана и поставлена в очередь |
| `task.started` | Job получил слот и начал выполнение |
| `task.progress` | Обновление прогресса |
| `task.completed` / `task.failed` | Задача финализирована |

### Прогресс задачи

Каждая задача парсинга отдаёт реал-тайм прогресс (WS-событие `task.progress`):

```json
{
  "current": 14,
  "total": 47,
  "stage": "parsing_vacancy",
  "message": "Парсинг вакансии 14 из 47"
}
```

---

## 7. Что сохраняется при парсинге

Обязательный минимум данных:

- `hh_vacancy_id`
- URL
- Название вакансии
- Компания
- Зарплата (от/до + валюта)
- Опыт, формат работы, график, занятость
- Город/регион
- Дата публикации
- Очищенное описание (текст)
- Опционально: сырой HTML (для отладки)

Лишняя информация (сайдбары, похожие вакансии, реклама, скрипты) — полностью отбрасывается.

---

## 8. Дедупликация и обновление

- Уникальный ключ: `(user_id, hh_vacancy_id)`
- При повторном добавлении:
  - если статус `raw` → обновляем данные;
  - если уже есть анализ/письмо → обновляем только после успешного нового анализа и генерации письма;
- Статус `applied` не перезаписывается автоматически.

---

## 9. Рекомендации по эксплуатации

- Использовать качественные резидентные прокси с хорошей ротацией
- Вести мониторинг процента успешных запросов и частоты капчи
- При росте доли капчи > 5% — автоматически снижать интенсивность парсинга
- Логировать все случаи срабатывания защиты для последующего улучшения Anti-Ban Module

## 10. Мульти-источниковая архитектура (адаптеры источников)

Подготовка к подключению новых job board без правок оркестратора, очереди и
API. hh.ru остаётся первым и пока единственным источником: его логика вынесена
в отдельный адаптер **без изменений поведения** — fallback chain (§2),
Anti-Ban (§3), режимы (§4), дедупликация (§8) сохранены полностью.

Код: `backend/app/modules/parsing/sources/` — `base.py` (контракт),
`hh.py` (`HHAdapter`), `registry.py` (`SourceRegistry`).

### 10.1. Контракт адаптера (`BaseSourceAdapter`)

Абстрактный базовый класс задаёт обязательный контракт каждого источника:

| Член | Назначение |
|------|------------|
| `source_name` | уникальное имя источника в реестре (для hh — «hh») |
| `search(filters) -> list[dict]` | сбор сырых карточек выдачи по фильтрам источника (ключевые слова, фильтры, `max_pages`, готовая ссылка выдачи) |
| `get_vacancy(external_id_or_url) -> dict \| None` | одна вакансия по внешнему id или прямой ссылке; `None` — вакансия удалена/не найдена (§5 → `not_found`) |
| `normalize(raw) -> dict` | маппинг сырых данных в каноническую схему (§7) |

Каноническая схема `normalize`: `source`, `external_id`, `url`, `title`,
`company_name`, `salary_from/to/currency`, `experience`, `employment_form`,
`work_format`, `schedule`, `area`, `published_at`, `description_raw`,
`description_html`.

**Anti-ban не входит в контракт адаптера.** Fallback chain curl_cffi →
Playwright + stealth (§2), прогрев сессии, паузы 4–8 с, ротация прокси и
обработка капчи (§3) остаются в Proxy & Anti-Ban Module: адаптер получает
готовую `AntiBanSession` и эту логику не дублирует.

### 10.2. ParsingOrchestrator и источники

- Конструктор: `ParsingOrchestrator(sources=None, registry=None)`; по
  умолчанию `sources = ["hh"]` (`DEFAULT_SOURCES`) — режимы и эндпоинты
  `/parsing/auto`, `/parsing/group`, `/parsing/manual` работают без изменений.
- Все адаптеры создаются через `SourceRegistry.create(...)` с **общей**
  `AntiBanSession` оркестратора (единые прокси, паузы и статистика трафика).
- Автопоиск (§4.1) перебирает все источники из `sources` и складывает итоги;
  групповой (§4.2) и ручной (§4.3) используют основной источник — первый
  в списке.
- Прогресс (§6), лимит `max_pages` (§4.1–§4.2), чёрный список (§4.9) и
  сохранение/дедупликация в БД (§8) остаются на оркестраторе; адаптеру
  оркестратор делегирует только URL-логику и разбор: `build_search_url`,
  `validate_search_url`, `page_url`, `parse_listing`, `build_vacancy_url`,
  `extract_fields` (хуки `BaseSourceAdapter`, §10.1).

### 10.3. Реестр источников (`SourceRegistry`)

Реестр — единственная точка подключения источников:

| Метод | Назначение |
|-------|------------|
| `register(adapter)` | зарегистрировать класс или экземпляр адаптера по `source_name` |
| `get(source_name)` | достать зарегистрированный адаптер; неизвестный источник → `UnknownSourceError` |
| `create(source_name, **kwargs)` | экземпляр адаптера (класс инстанцируется с kwargs, например `session=...`) |
| `execute(source_name, method, ...)` | исполнить метод адаптера по имени источника (синхронный или async) |
| `names()` | список зарегистрированных источников |

`default_registry()` возвращает реестр со встроенным `HHAdapter`.
Новый источник = класс-наследник `BaseSourceAdapter` + `register(...)`.

### 10.4. БД: `source`, `external_id` и дедупликация

Таблица `vacancies` (docs/02 §3.3) дополнена полями мульти-источникового
парсинга:

| Поле | Тип | Описание |
|------|-----|----------|
| `source` | `VARCHAR(32) NOT NULL`, default `'hh'` | Источник вакансии. `'hh'` — значение по умолчанию (площадка, задаётся адаптером); значения `'auto'/'group'/'manual'` сохранены как режим ввода — фильтр `GET /vacancies?source=...` и контракт docs/02 §3.3 продолжают работать (CHECK `ck_vacancies_source` расширен допустимым `'hh'`) |
| `external_id` | `VARCHAR(32) NOT NULL` | Внешний идентификатор вакансии у источника. Для hh — generated-колонка `GENERATED ALWAYS AS (hh_vacancy_id) STORED`: код хранения не менялся, а колонка всегда заполнена |

Составной уникальный индекс
`uq_vacancies_user_source_external (user_id, source, external_id)` —
**дубликат вакансии одного источника невозможен**. Существующий ключ
`(user_id, hh_vacancy_id)` (§8) сохранён: он по-прежнему гарантирует
дедупликацию hh-вакансий между режимами ввода.

> Миграции: изменения `models.py` применяются к существующей БД через
> `alembic upgrade head`; в тестовой БД схема пересоздаётся из
> `Base.metadata` (conftest: `drop_all` + `create_all`).
